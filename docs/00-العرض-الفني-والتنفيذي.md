## مشروع نظام إدارة المدرسة الذكي

| البند | القيمة |

| نوع المستند | عرض فني وتنفيذي (Pre-Implementation Proposal) |

## القسم 1: التحليل الفني

### 1.1 قراءة المشروع
المشروع نظام تشغيلي مدرسي حقيقي (وليس نموذجاً)، مركزه ميزة واحدة حاسمة: **الحضور التلقائي بالتعرّف على الوجه عبر هاتف مثبّت عند المدخل**، مع نظام إداري كامل على الحاسوب، وقاعدة بيانات مركزية، وصلاحيات مطبّقة من جهة الخادم.

### 1.2 إعادة صياغة المتطلبات كمكوّنات قابلة للتنفيذ
| الرقم | المكوّن | الوصف المختصر | الأولوية |
|---|---|---|---|
| C1 | خدمة الوجه على الجهاز (Android) | كشف + استخراج السمات + مطابقة محلياً | حرجة |
| C2 | شاشة الحضور المستمرة | كاميرا مفتوحة، اكتشاف متتابع، عرض النتيجة | حرجة |
| C3 | الخادم + API | منطق العمل، الصلاحيات، القيود | حرجة |
| C4 | قاعدة البيانات المركزية | كيانات المدرسة + قيود منع التكرار | حرجة |
| C5 | نظام الحاسوب (ويب) | لوحة تحكم + إدارة + تقارير + طباعة | عالية |
| C6 | إدارة الطلاب والصفوف | ملفات، شعب، ترحيل، استيراد | عالية |
| C7 | الدرجات والامتحانات | مواد، امتحانات، مجاميع، كشوف | عالية |
| C8 | التقارير | 14 تقريراً + PDF/Excel + صلاحيات | عالية |
| C9 | الصلاحيات والأدوار | تطبيق من الخادم لا من الواجهة | حرجة |
| C10 | سجل التدقيق والنسخ الاحتياطي | Audit log + Backup/Restore | عالية |
| C11 | العمل دون إنترنت والمزامنة | طابور محلي + منع تكرار + معالجة تعارض | عالية |
| C12 | الأمان والخصوصية | تشفير، إخفاء أسرار، احتفاظ/حذف | حرجة |

### 1.3 القيود والمخاطر التقنية المؤثرة على التصميم
1. **الحضور ميزة زمنها حساس**: أي إرسال صورة للخادم في كل مرة يضيف زمن شبكة غير مقبول. القرار: المعالجة محلياً على الهاتف (On-device)، والخادم يستقبل فقط «حدث حضور موقّعاً» وليس الصور.
2. **اختلاف مواصفات الهواتف**: الأداء يعتمد على الجهاز. لذلك تُحدَّد أهداف الأداء **بعد** تحديد الهاتف المستهدف (قسم 6)، وتُقاس فعلياً (قسم 8).
3. **الخصوصية الحيوية**: لا تُخزَّن الصور الأصلية افتراضياً؛ يُخزَّن تمثيل السمات (Embedding) فقط (تفصيل في القسم 5 والقسم 9).
4. **تعدد الوجوه في الإطار**: لا يجوز افتراض طالب واحد لكل إطار؛ يجب دعم عدة اكتشافات في الإطار الواحد (قسم 4).
5. **منع التكرار تحت انقطاع الشبكة**: يلزم معرّف عملية فريد (UUID) + قيد فريد في قاعدة البيانات (قسم 4 و11).

### 1.4 الافتراضات (تحتاج تأكيداً)
- عدد الطلاب المتوقع في المدى: 300 – 2000 طالب لكل مدرسة.
- المدرسة واحدة عند الإطلاق، والتصميم يدعم تعدد المدارس (Multi-tenant) لاحقاً.
- المنطقة الزمنية: `Asia/Baghdad` (UTC+3)، والوقت المعتمد للتحقق هو وقت الخادم.
- فترة الحضور الصباحي: نافذة زمنية قابلة للضبط (افتراض مبدئي 30–45 دقيقة).
- وجود شبكة Wi-Fi محلية موثوقة في المدرسة (حتى مع انقطاع الإنترنت الخارجي).

## القسم 2: المعمارية المقترحة

### 2.1 نظرة عامة (طبقات منفصلة)
```
        ┌──────────────────────┐        ┌───────────────────────────┐
        │  تطبيق Android        │        │  نظام الحاسوب (ويب)        │
        │  (شاشة الحضور)        │        │  متصفح على Windows         │
        │  • كاميرا             │        │  • لوحة تحكم               │
        │  • كشف/سمات/مطابقة    │        │  • إدارة/تقارير/طباعة       │
        │    محلياً (On-device) │        │                            │
        │  • طابور محلي آمن     │        │                            │
        └──────────┬───────────┘        └─────────────┬─────────────┘
                   │  HTTPS + JWT                      │ HTTPS + JWT
                   ▼                                   ▼
        ┌───────────────────────────────────────────────────────────┐
        │                    الخادم (Backend API)                     │
        │  • المصادقة والتفويض (RBAC من الخادم)                       │
        │  • منطق الأعمال: حضور/انصراف/تأخير/درجات/تقارير             │
        │  • قيود منع التكرار + Audit Log                             │
        │  • توليد PDF/Excel + النسخ الاحتياطي                        │
        └──────────────────────────┬────────────────────────────────┘
                                   │
                    ┌──────────────┴───────────────┐
                    ▼                              ▼
        ┌───────────────────────┐      ┌───────────────────────────┐
        │  قاعدة البيانات        │      │  تخزين ملفات/نسخ احتياطي   │
        │  PostgreSQL            │      │  (مشفّر)                   │
        └───────────────────────┘      └───────────────────────────┘
```

### 2.2 مبدأ الفصل
- **الواجهة** (Android / Web) لا تحتوي منطق الصلاحيات؛ تعرض فقط ما يسمح به الخادم.
- **منطق الأعمال** كله في الخادم: القواعد الزمنية، منع التكرار، حساب الغياب/التأخير، النجاح/الرسوب.
- **قاعدة البيانات** هي مصدر الحقيقة الوحيد، وفيها القيود النهائية (Unique constraints) التي تمنع التكرار حتى لو تجاوزت الواجهة القواعد.

### 2.3 تدفّق تسجيل الحضور بالتعرّف على الوجه (التسلسل)
```
الطالب يمرّ وينظر  →  الكاميرا تلتقط الإطار
      →  كشف الوجوه (يدعم أكثر من وجه في الإطار)
      →  استخراج السمات لكل وجه (محلياً)
      →  المطابقة مع فهرس السمات المحفوظ محلياً (بحث متجهي سريع)
      →  عتبة الثقة:
             • ثقة عالية + هوية واحدة  → قبول
             • ثقة منخفضة أو التباس      → "تعذّر التعرّف" → قائمة مراجعة
      →  تحقّق قواعد الدوام (النافذة الزمنية، الحالة، عدم التكرار)
      →  توليد حدث حضور بمعرّف فريد (UUID) + وقت الخادم
      →  إرسال للخادم (أو إيداعه في الطابور المحلي إذا انقطع الاتصال)
      →  إظهار النتيجة: الاسم + الصف + الشعبة + الوقت + صوت اختياري
      →  عودة فورية لوضع الاستعداد (بالتوازي مع إظهار النتيجة)
```

### 2.4 مبادئ الأداء
- لا يُنتظر انتهاء الصوت أو عرض الرسالة قبل معالجة الإطار التالي (إظهار النتيجة والعودة للاستعداد متوازيان).
- آلية **مهلة/تبريد (Cooldown)** تمنع احتساب الوجه نفسه مراراً أثناء بقائه أمام الكاميرا، دون منع تسجيل لاحق مشروع بعد مغادرة المكان.
- فهرس السمات في الذاكرة للبحث السريع، وليس مسحاً خطياً لكل السجلات.

## القسم 3: التقنيات وقاعدة البيانات

### 3.1 التقنيات المقترحة (مبرَّرة)

| الطبقة | الاختيار المقترح | البديل | سبب الاختيار |
|---|---|---|---|
| تطبيق Android | **Kotlin + Jetpack Compose + CameraX** | Java + XML | أحدث، رسمي، أداء جيد، دعم مباشر لتحليل الإطارات |
| معالجة الوجه | **Google ML Kit Face Detection** + **مطابقة محلية بـ Embeddings** (مثل MobileFaceNet عبر TFLite/LiteRT) | إرسال الصور للخادم | معالجة محلية: أسرع، أقل شبكة، أقل خصوصية مخاطرة |
| الخادم | **Python + FastAPI** | Node.js/NestJS أو .NET | سريع التطوير، توثيق API تلقائي (OpenAPI)، أداء جيد، مناسب للتقارير |
| قاعدة البيانات | **PostgreSQL** | MySQL | قيود Unique قوية، JSONB، أداء جيد، دعم امتدادات المتجهات لاحقاً |
| نظام الحاسوب | **تطبيق ويب (React/Next.js + Tailwind، RTL)** | تطبيق Windows مكتبي | نفس الكود يعمل على أي متصفح، تحديث مركزي أسهل، طباعة وتصدير أفضل، صيانة أرخص |
| PDF / Excel | مكتبات خادم (ReportLab/openpyxl أو ما يكافئها) | أدوات واجهة | توليد مركزي موحّد ومقيّد بالصلاحيات |
| المزامنة | طابور محلي (Room/SQLite) + UUID + Idempotency Key | — | يمنع التكرار ويسمح بالعمل دون إنترنت |
| النشر | Docker + Nginx + شهادة TLS | نشر تقليدي | قابلية النقل وإعادة البناء والاستعادة |

> **ملاحظة مهمة عن تطبيق الحاسوب:** التوصية هي **تطبيق ويب احترافي** يُفتح من المتصفح على Windows. المقارنة الكاملة بين الويب والمكتبي في القسم 12.

### 3.2 مخطط قاعدة البيانات
المخطط التفصيلي (الجداول، الحقول، العلاقات، القيود، الفهارس) في ملف مستقل:
`docs/01-مخطط-قاعدة-البيانات.md`

الكيانات الرئيسية: المدارس، السنوات الدراسية، المراحل، الصفوف، الشعب، الطلاب، أولياء الأمور، المدرسون، المواد، التكليفات، الامتحانات، الدرجات، المستخدمون، الأدوار، الصلاحيات، الأجهزة، جلسات الحضور، سجلات الحضور، سجلات الغياب، الإجازات، الحالات الاستثنائية، قائمة المراجعة، سجل التدقيق، إعدادات النظام، تمثيلات الوجه (Biometric Templates).

### 3.3 لماذا PostgreSQL تحديداً؟
1. **قيود تمنع التكرار على مستوى القاعدة**: `UNIQUE(student_id, date, session_type)` — حتى لو أرسل الهاتف الحدث مرتين، ترفضه القاعدة.
2. **معاملات ACID** لسلامة الدرجات والحضور.
3. **JSONB** للإعدادات المرنة (قواعد الدوام، النجاح/الرسوب) دون تعديل الكود.
4. **قابلية التوسّع** إلى `pgvector` للمطابقة على الخادم مستقبلاً إن لزم.

## القسم 4: تصميم نظام الحضور بالتعرّف على الوجه (تفصيلي)

هذا القسم هو جوهر المشروع.

### 4.1 أين تحدث المعالجة؟
**القرار: المعالجة محلياً على الهاتف (On-device).**
- الكاميرا → كشف الوجوه → استخراج السمات → المطابقة على فهرس محلي.
- **لا تُرسل الصور إلى الخادم** أثناء التشغيل الاعتيادي.
- الخادم يستقبل **حدث حضور** فقط: (student_id، وقت الخادم، device_id، UUID، درجة الثقة).
- **السبب**: تقليل الزمن (لا انتظار شبكة)، تقليل استهلاك البيانات، تقليل مخاطر الخصوصية، والعمل عند انقطاع الإنترنت.

### 4.2 الدقة ومنع الأخطاء (مطابقة المتطلبات 1–12 في القسم الثالث)
| المتطلب | آلية التنفيذ |
|---|---|
| منع تسجيل الطالب مرتين في الفترة | قيد `UNIQUE` في القاعدة + فحص في الخادم + UUID للحدث |
| المعرّف الثابت | `student_number` هو المعرّف، الاسم للعرض فقط |
| منع الربط الخاطئ | عتبة ثقة صارمة + هامش فصل بين أفضل تطابقين (Margin) |
| الثقة غير الكافية | عرض «تعذّر التعرّف» بدل تخمين الاسم |
| مراجعة الحالات الملتبسة | جدول `recognition_reviews` + شاشة مراجعة |
| منع الوجوه غير المسجّلة | لا مطابقة تحت العتبة = لا تسجيل |
| فصل السجلات | `attendance_records` منفصل عن `recognition_attempts` |
| الوجوه المتداخلة | الكشف يعيد عدة وجوه لكل إطار؛ تُعالج كلها |
| المهلة/التبريد | Cooldown زمني لكل هوية + شرط مغادرة الإطار قبل إعادة الاحتساب |
| تعديل يدوي موثّق | كل تعديل يُسجَّل في `audit_log` مع المستخدم والوقت والسبب |
| تصحيح سجل خاطئ | صلاحية مخصّصة + الاحتفاظ بالسجل الأصلي (لا حذف) |
| لا تسجيل عند الالتباس/الجودة الرديئة | رفض تلقائي + إرسال للمراجعة |

### 4.3 العتبات والأهداف القابلة للقياس
> لا نعلن أرقاماً غير مثبتة. تُحدَّد الأهداف التالية **بعد** اختيار الهاتف، وتُقاس فعلياً:

| المؤشر | طريقة القياس | الهدف (يُعتمد بعد القياس الأولي) |
|---|---|---|
| زمن الكشف للوجه | قياس من الإطار إلى نتيجة الكشف | يُحدَّد بعد قياس الجهاز |
| زمن المطابقة | قياس من السمات إلى أفضل تطابق | يُحدَّد بعد القياس |
| الزمن الكلي حتى التسجيل | من ظهور الوجه إلى حدث الحضور | يُحدَّد بعد القياس |
| معدل القبول الخاطئ (FAR) | مجموعة اختبار موجّهة | يُحدَّد حسب سياسة المدرسة |
| معدل الرفض الخاطئ (FRR) | مجموعة اختبار موجّهة | يُحدَّد حسب سياسة المدرسة |
| زمن الاستعداد للطالب التالي | قياس فعلي | يُحدَّد بعد القياس |

### 4.4 مؤشرات التشغيل على الشاشة
- عدد المسجّلين بنجاح اليوم.
- عدد الحالات التي تحتاج مراجعة.
- عدد السجلات غير المزامنة (عند انقطاع الاتصال).
- حالة الكاميرا والاتصال.

### 4.5 مقاومة الصور المزيّفة (Anti-Spoofing)
- استخدام خاصية كشف الحيوية إن توفّرت في مكتبة الكشف.
- **لا ندّعي حماية 100%**؛ مستوى الحماية يعتمد على الكاميرا والتقنية.
- اختبار صور العرض (شاشة/ورق) ضمن حدود التقنية، وتوثيق النتائج الفعلية.

## القسم 5: الخصوصية الحيوية وبيانات الوجه

### 5.1 ما الذي يُخزَّن؟
**القرار الافتراضي: تخزين تمثيل السمات (Embedding) فقط، لا الصور الأصلية.**
| العنصر | يُخزَّن؟ | السبب |
|---|---|---|
| الصور الأصلية | لا (افتراضياً) | تقليل البيانات الحساسة إلى الحد الضروري |
| تمثيل السمات (Vector) | نعم | ضروري للمطابقة، ويُشفَّر عند التخزين |
| معرّف الطالب المرتبط | نعم | الربط الصحيح |
| تاريخ التسجيل/التحديث | نعم | للتدقيق |
| حالة التفعيل/التعطيل | نعم | تعطيل التعرّف دون حذف الملف المدرسي |

> إذا احتاجت المدرسة تخزين الصور الأصلية لأي سبب، يُطلب قرار كتابي + أساس قانوني + سياسة احتفاظ، ويُشفَّر التخزين.

### 5.2 الضوابط
- لا يبدأ التسجيل البيومتري قبل استكمال الموافقات القانونية المعتمدة.
- موظف مخوّل فقط ينفّذ التسجيل.
- فحص جودة الصورة قبل الاعتماد، ورفض الصور غير المناسبة.
- تقييد الوصول للسمات، وتشفيرها، وعدم عرضها لغير المخوّلين.
- تحديد مكان التخزين ومدة الاحتفاظ وآلية الحذف.
- طريقة بديلة لتسجيل الحضور لمن لا يستخدم التعرّف على الوجه.

### 5.3 الاحتفاظ والحذف
| البيانات | مدة الاحتفاظ الافتراضية | آلية الحذف |
|---|---|---|
| تمثيل السمات | طوال بقاء الطالب مسجّلاً + فصل دراسي | حذف عند التخرّج/الانسحاب وفق السياسة |
| سجلات الحضور | حسب سياسة المدرسة (سنوات دراسية) | أرشفة ثم حذف بصلاحية معتمدة |
| سجل التدقيق | مدة أطول (للمساءلة) | أرشفة، ولا يُحذف إلا بإجراء معتمد |
| النسخ الاحتياطية | دورية ومشفّرة | إتلاف آمن وفق السياسة |

## القسم 6: متطلبات الأجهزة

### 6.1 أجهزة الحضور (Android)
| البند | التوصية |
|---|---|
| النظام | Android 10 أو أحدث (يُثبَّت نهائياً بعد تحديد الأجهزة) |
| الذاكرة | RAM ≥ 4GB (الأفضل 6GB+) |
| الكاميرا | خلفية ≥ 8MP، تثبيت ثابت عند المدخل، إضاءة كافية |
| التثبيت | حامل ثابت بزاوية مناسبة لمرور الطلاب |
| التوصيل | Wi-Fi مستقر + شاحن دائم |
| التطبيق | تطبيق أصلي قابل للتثبيت (APK/AAB)، وليس WebView |

> يُحدَّد الطراز النهائي بعد قياس الأداء الفعلي على جهاز مرشّح واحد على الأقل (قسم 8، المرحلة الخامسة).

### 6.2 خادم المدرسة

## القسم 9: معايير القبول والاختبار

### 9.1 اختبارات الوظائف
إنشاء/تعديل طالب، استيراد قائمة، تسجيل حضور، منع التكرار، حساب غياب/تأخير، انصراف، تعديل بصلاحية، تقارير، درجات، تطبيق الصلاحيات.

### 9.2 اختبارات التعرّف على الوجه
زمن الكشف/المطابقة/التسجيل، مرور متتابع، أكثر من وجه في الإطار، إضاءة جيدة/ضعيفة، مسافات وزوايا، حالات عدم التعرّف، FAR/FRR، منع التكرار، صور عرض مزيّفة، استمرارية دوام فعلي.

### 9.3 اختبارات الأداء
عدد الطلاب الفعلي، قاعدة البيانات عند ارتفاع السجلات، البحث والتقارير، تعدد المستخدمين، استهلاك الذاكرة/المعالج/البطارية، عدم تجمّد شاشة الحضور.

### 9.4 اختبارات الشبكة
انقطاع/عودة، تكرار الإرسال، تأخر الاستجابة، فقدان الخادم، إعادة تشغيل الهاتف والتطبيق.

### 9.5 اختبارات الأمان
وصول غير مصرّح، تعديل دون صلاحية، تعطيل حساب وإبطال الجلسة، استعادة نسخة احتياطية، التأكد من عدم وجود أسرار داخل التطبيق، حماية البيانات الحساسة.

### 9.6 نموذج معيار قبول كل ميزة
| الحقل | الوصف |
|---|---|
| الميزة | اسم الميزة |
| معيار القبول | سلوك قابل للقياس |
| طريقة الإثبات | اختبار/لقطة/تقرير |
| النتيجة | ناجح/راسب |
| الملاحظات | مشكلات وإصلاحات |

### 9.7 شروط القبول النهائية
مطابقة للقسم العشرين من وثيقتك: تشغيل فعلي، قاعدة بيانات واحدة، عمليات الطلاب، حفظ الحضور، منع التكرار، صلاحيات من الخادم، صحة التقارير، تصدير/طباعة، نسخ احتياطي/استعادة، نجاح الاختبارات، توثيق سرعة/دقة، لا بيانات وهمية، نسخة Android قابلة للتثبيت، طريقة تشغيل الحاسوب، الكود المصدري، توثيق القاعدة/API، تعليمات الصيانة، وتوثيق أي ميزة غير منفّذة.

## القسم 10: خطة التسليم والدعم والصيانة

### 10.1 عناصر التسليم
- تطبيق Android قابل للتثبيت + كوده المصدري.

- بيان التكاليف المتكررة.

## القسم 14: إجابات الأسئلة الـ23 (القسم 23 من وثيقتك)

1. **تقنية تطبيق Android؟** Kotlin + Jetpack Compose + CameraX، تطبيق أصلي قابل للتثبيت.
2. **تقنية نظام الحاسوب؟** تطبيق ويب احترافي (React/Next.js) يعمل على Windows من المتصفح.
3. **نوع قاعدة البيانات ولماذا؟** PostgreSQL لقيودها القوية (منع التكرار)، ومعاملاتها، ومرونتها.
4. **تقنية التعرّف على الوجه وترخيصها؟** ML Kit (كشف) + نموذج Embeddings مفتوح المصدر (مثل MobileFaceNet) — راجع الترخيص قبل الاعتماد النهائي.
5. **محلي أم خادم؟** محلي على الهاتف افتراضياً؛ الخادم يستقبل أحداث الحضور فقط.
6. **مطابقة سريعة دون إرسال صور؟** نعم، عبر فهرس سمات محلي.
7. **الأداء المتوقع وقياسه؟** يُحدَّد بعد قياس فعلي على الجهاز المستهدف (قسم 4.3).
8. **العدد الذي يتحمّله النظام؟** مصمّم لـ 300–2000 طالب/مدرسة، ويُختبر فعلياً.
9. **منع الخلط والتكرار؟** عتبة ثقة + هامش فصل + UUID + قيد Unique في القاعدة.
10. **عند انقطاع الإنترنت؟** طابور محلي مشفّر + مزامنة لاحقة + معالجة تعارض.
11. **الأجهزة والكاميرات؟** Android 10+، RAM 4GB+، كاميرا 8MP+ ثابتة عند المدخل.
12. **تكاليف ترخيص/خدمات خارجية؟** المكتبات مفتوحة المصدر غالباً؛ لا خدمات مدفوعة دون موافقة.
13. **تكلفة الاستضافة شهرياً/سنوياً؟** تقديرياً 10–50 $/شهر (قسم 11).
14. **حماية بيانات الوجه وحذفها؟** تشفير + صلاحيات + سياسة احتفاظ/حذف (قسم 5).
15. **نقل البيانات عند تغيير المطوّر/الاستضافة؟** نسخ احتياطي + تصدير + ملكية باسم المدرسة.
16. **مدة كل مرحلة؟** قسم 7.1.
17. **شروط الدعم والصيانة؟** قسم 10.2.
18. **ما يدخل في السعر وما يعد إضافياً؟** يُحدَّد في العقد بعد اعتماد النطاق (قسم 13).
19. **هل أستلم الكود الكامل والملفات لإعادة البناء؟** نعم (قسم 10.1).
20. **كيف يُثبت أن المشروع حقيقي؟** تشغيل فعلي + نتائج اختبارات موثّقة + معايير قبول (قسم 9).
21. **هل يدعم أكثر من مدرسة مستقبلاً؟** نعم، التصميم يدعم Multi-tenant.
22. **طريقة التسجيل البديلة لمن لا يستخدم الوجه؟** تسجيل يدوي/بحث بالرقم المدرسي.
23. **كيف تُحدَّث بيانات الطلاب على الأجهزة؟** مزامنة دورية + تحديث الفهرس عند التغيير.
